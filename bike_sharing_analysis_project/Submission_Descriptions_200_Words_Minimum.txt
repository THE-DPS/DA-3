WEEK 1 DESCRIPTION
============================================================================
This report presents the Week 1 planning stage of an end-to-end data analysis project focused on historical bike-sharing demand. It defines the operational problem, the principal research questions, the intended target variable, the proposed predictor groups, and the project boundaries. The analysis uses the UCI Bike Sharing dataset, which contains daily and hourly rental counts alongside calendar, seasonal, and weather information. The daily file is selected so that the outcome is consistently measured at the daily level. The report reviews the dataset’s provenance and relevant analytical resources, then translates best practices into a practical workflow covering data acquisition, profiling, cleaning, exploratory data analysis, regression modeling, validation, and dashboard communication.

The methodology section explains the planned use of Python, Pandas, NumPy, Matplotlib, Seaborn, scikit-learn, and Streamlit, with a rationale for each tool. It also proposes a realistic time allocation, reproducibility practices, and success criteria. Risk assessment is a central component: the report addresses the dataset’s historical coverage, limited geographic scope, possible correlated features, outlier interpretation, temporal validation, and the risk of target leakage. In particular, the component counts for casual and registered users are excluded from the predictor set because they sum to the total rental count. The report is intended to establish a defensible analytical blueprint before coding begins. The final project will only make numerical claims after the accompanying scripts have been run and their outputs reviewed. The dataset creator and UCI repository are credited, and the limitations of observational data are made explicit.

WEEK 2 DESCRIPTION
============================================================================
This Week 2 report documents a reproducible workflow for acquiring, profiling, and preparing the UCI Bike Sharing daily dataset for analysis. It identifies the official repository as the primary source, records the dataset citation and license information, and explains why the daily and hourly files must not be combined: they represent the same service activity at different aggregation levels. The report describes the key fields, identifies total daily rentals as the modeling target, and specifies which columns must be excluded to prevent leakage. It also outlines an audit-friendly data profiling process covering row and column counts, data types, missingness, duplicate rows and dates, category values, date coverage, numerical ranges, and target validity.

The cleaning strategy is intentionally conservative. Dates are parsed into a proper datetime type; missingness is measured before any imputation; duplicate records are investigated rather than automatically deleted; and extreme values are flagged for contextual review instead of being removed solely because they lie beyond an IQR fence. The report explains how numerical and categorical imputation, one-hot encoding, and scaling can be handled within scikit-learn pipelines when required, so preprocessing is learned only from training data. It includes illustrative before-and-after examples and distinguishes those examples from measured results. The companion Python project contains acquisition and preparation scripts that save a cleaned CSV and a machine-readable profiling summary. Legal and ethical considerations include attribution, respect for the stated license, transparent documentation, and avoidance of causal claims about individual behavior. Actual row counts and cleaning outcomes should be taken from the generated outputs after the code is executed.

This Week 3 report outlines a structured exploratory data analysis of the prepared daily bike-sharing dataset. Its purpose is to characterize the target distribution, identify temporal and categorical patterns, explore relationships between weather variables and rental counts, and inform the next modeling stage. The report begins with a dataset summary and recommends descriptive statistics such as mean, median, standard deviation, quartiles, range, category counts, and proportions. It explains how Pandas group-by operations and descriptive summaries can support comparisons by month, weekday, season, and weather situation. For each chart type, the report explains why it fits the analytical question and what limitations should be considered. It also provides an interpretation framework that separates observed patterns from plausible explanations and avoids claiming causation from correlation. Outliers are treated as observations requiring investigation, not automatic errors. The report details the roles of Pandas, Matplotlib, Seaborn, and optional Plotly interactivity, as well as visual quality controls such as clear labels, readable axes, appropriate bins, and sample-size awareness. The accompanying script generates reproducible figures and summary tables. The final interpretation must be aligned with those executed outputs rather than relying on assumed or invented patterns.

WEEK 4 DESCRIPTION
============================================================================
This Week 4 report documents a reproducible statistical modeling strategy for predicting daily bike-sharing demand. The target is total daily rentals, while calendar and normalized weather variables are candidate predictors. The report compares a training-period mean baseline, Linear Regression, and a tuned Random Forest regressor. It explains why a simple baseline is necessary and why a nonlinear model may capture interactions that a linear model misses, while also emphasizing that model complexity is not evidence of superior performance. The feature design explicitly excludes the casual and registered user counts because they sum to the target, and excludes the record index as a predictor. These safeguards reduce direct target leakage and improve the credibility of the evaluation.

The report recommends sorting records chronologically, reserving the latest 20 percent for a final test set, and using time-aware cross-validation only within the training period for model selection. All imputing and categorical encoding are placed in scikit-learn pipelines to prevent preprocessing leakage across folds. The evaluation framework includes Mean Absolute Error, Root Mean Squared Error, and R-squared, with explanations of what each metric measures and what it cannot establish alone. Residual diagnostics and actual-versus-predicted plots are recommended to identify systematic errors. The report also discusses linear-model assumptions, Random Forest limitations, uncertainty, and the distinction between predictive feature importance and causal effects. The included training script saves model metrics, predictions, and the selected model artifact. No model score is invented in the report; the final performance narrative must use the values generated by running the code and must identify the test period and limitations.

The accompanying app is runnable locally after the project scripts generate the necessary data and metrics. The report makes clear that this is a historical demonstration, not a live forecasting service or a production deployment.
